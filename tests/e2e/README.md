# Gatehouse end-to-end tests (Playwright)

## Prerequisites

1. Docker running.
2. The whole system running from the repository root (keep it running in another terminal):

   ```bash
   dotnet run --project src/Gatehouse.AppHost
   ```

   Wait until `web` is `Running` in the Aspire dashboard (http://localhost:3000 answers).
3. The demo user password exported (generated by the AppHost, stored in its user secrets):

   ```bash
   export GATEHOUSE_DEMO_PASSWORD="$(dotnet user-secrets list --project src/Gatehouse.AppHost | sed -n 's/^Parameters:demo-user-password = //p')"
   ```

Optional: `GATEHOUSE_WEB_URL` (default `http://localhost:3000`), `GATEHOUSE_API_URL` (default `http://localhost:5048`, the
AppHost `api` resource), `GATEHOUSE_KEYCLOAK_URL` (default `http://localhost:8080`).

## Rules

- **Readiness first.** `warmup.setup.ts` runs before every spec and waits (polled, at most 4 minutes together) for API
  `GET {GATEHOUSE_API_URL}/health` = 200, Keycloak discovery of realm `gatehouse` (with `issuer`) and one signed-in data
  call (a demo user signs in through the BFF and `/api/proxy/v1/sites` returns at least one site), then compiles the
  sign-in routes. A freshly started AppHost therefore passes on the first run.
- **Specs never depend on data left by other specs** (or by earlier runs). A spec creates what it asserts on (its own
  request and approval, its own door scenario), clears simulator scenarios and open alarms it relies on first, and asserts
  on the records it created (by door and time, by id) or on changes relative to a value it read, never on absolute counts.

The M10 onboarding specs (`onboarding/`) also need these AppHost user secrets (they are generated on the first AppHost run):

```bash
s() { dotnet user-secrets list --project src/Gatehouse.AppHost | sed -n "s/^Parameters:$1 = //p"; }
export GATEHOUSE_PLATFORM_OPERATOR_PASSWORD="$(s platform-operator-password)" GATEHOUSE_PLATFORM_OTP_SECRET="$(s platform-operator-otp-secret)"
export GATEHOUSE_ACME_BROKER_CLIENT_SECRET="$(s acme-broker-client-secret)" GATEHOUSE_UPSTREAM_IDP_ADMIN_PASSWORD="$(s upstream-idp-password)"
export GATEHOUSE_POSTGRES_PASSWORD="$(s postgres-password)"
```

These suites (and the AppHost tests, `dotnet test tests/Gatehouse.IntegrationTests --filter "Category=AppHost"`) run only
locally during development, not in CI: run them before merging a change that touches sign-in, onboarding, connectors or the
live view. After editing `infra/keycloak/`, reset Keycloak first (CLAUDE.md, "Reset Keycloak").

## Run

```bash
cd tests/e2e
npm ci
npx playwright install chromium
npx playwright test auth/
```

The HTML report is written to `playwright-report/` (not opened automatically). Stop the AppHost afterwards.

## Leftover test tenants

Onboarding specs (`e2e-<stamp>`, `fixtures/platform.ts`) and scenario tests (`scn-<stamp>`, `ScenarioTenantFactory`) create a
tenant per run and do not delete it: the product has no tenant deletion (a platform endpoint for it would be a contract
change), and removing rows and databases from a test fixture would bypass the product and could hit a run in parallel. Each
leftover tenant is one more database that every background loop visits, so remove them now and then, against the local
AppHost Postgres only (the AppHost running, port 55432; never production):

```bash
PW=$(dotnet user-secrets list --project src/Gatehouse.AppHost | sed -n 's/^Parameters:postgres-password = //p')
export DOTNET_ENVIRONMENT=Development
export ConnectionStrings__postgres="Host=localhost;Port=55432;Username=postgres;Password=$PW"
export ConnectionStrings__catalog="$ConnectionStrings__postgres;Database=catalog"
dotnet run --project src/Gatehouse.Cli -- purge-test-tenants            # list
dotnet run --project src/Gatehouse.Cli -- purge-test-tenants --apply    # delete catalog rows + drop databases
```

The command refuses to run outside Development or against a non-local host. It deletes only `e2e-*`/`scn-*` tenants (catalog
rows and `gh_tenant_e2e_*`/`gh_tenant_scn_*` databases); it never removes Docker volumes, and their Keycloak organizations stay
in `gatehouse-keycloak-data`.
